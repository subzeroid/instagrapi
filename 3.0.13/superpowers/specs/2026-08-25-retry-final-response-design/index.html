    Retry final-response exception mapping

    Date: 2026-08-25 Issue: https://github.com/subzeroid/instagrapi/issues/2774 Status: Approved

    Problem

    The private and public requests sessions configure urllib3 retries for HTTP 429, 500, 502, 503, and 504. urllib3's default raise_on_status=True raises a requests.exceptions.RetryError when those retries are exhausted. That happens inside the transport adapter, before instagrapi receives the final HTTP response.

    As a result, _send_private_request() and _send_public_request() cannot apply their existing status mapping. In particular, a final HTTP 429 escapes as the transport-specific RetryError instead of instagrapi's ClientThrottledError.

    Goals

    • Preserve the configured retry count, status list, allowed methods, and backoff behavior.
    • Let instagrapi inspect the final HTTP response after retry exhaustion.
    • Preserve the existing typed exception mapping, including HTTP 429 to ClientThrottledError.
    • Prevent the public request loop from repeating a status that the Requests adapter has already retried to exhaustion.
    • Apply the same typed-error contract to private requests, ordinary public requests, and streaming public requests.
    • Add regression coverage that fails under the current configuration.

    Non-goals

    • Do not hide or automatically bypass Instagram rate limits.
    • Do not change the default number of retries or backoff timing.
    • Do not change login, challenge, CAA/Bloks payloads, or protocol selection.
    • Do not refactor feature mixins that call the raw Requests sessions directly; they receive the final response but continue to own their existing mapping or parsing behavior.
    • Do not infer why Instagram rate-limited a particular account or IP address.

    Considered approaches

    1. Return the final response after retries (selected)

    Set raise_on_status=False on both urllib3 Retry strategies. urllib3 still performs the configured retries, then returns the last HTTP response. The existing instagrapi request handlers call raise_for_status() and map the response to the appropriate typed exception.

    This is the smallest change and keeps HTTP semantics in the layer that already owns them.

    2. Catch and translate RetryError

    Catch requests.exceptions.RetryError around session calls and inspect its cause. This is rejected because Requests usually does not retain the final HTTP response on this exception, so translation would depend on exception text or urllib3 internals.

    3. Stop retrying HTTP 429

    Remove 429 from the default retry status list. This would expose a typed exception immediately, but it would also change the established retry policy and would not solve the same exception leak for 500, 502, 503, or 504.

    Design

    Add raise_on_status=False to both compatibility branches of PrivateRequestMixin._build_private_session_retry_strategy() and PublicRequestMixin._build_public_session_retry_strategy().

    In PublicRequestMixin.public_request(), stop the outer application retry loop when all of the following are true:

    • the mapped exception has a response status in session_retry_statuses;
    • session_retry_total is greater than zero, so the adapter already performed status retries.

    When session_retry_total=0, retain the existing outer public retry loop. This preserves the explicitly disabled-adapter configuration while preventing the default configuration from multiplying four transport attempts into twelve.

    In _send_public_request(), move the stream=True return until after last_public_response is assigned and raise_for_status() has run. Do not run the content-length completeness check or read the response body for a streaming request. HTTP failures therefore enter the existing public typed-exception mapping before the open response is returned to a successful caller.

    No new public API is introduced. Client.set_retry_config() continues to rebuild both adapters with the same user-configurable values. The final response reaches instagrapi instead of urllib3 raising first, and the public application loop does not repeat a status already exhausted by the adapter.

    Data flow after the change:

    1. Requests sends an HTTP request through the configured adapter.
    2. urllib3 retries configured status codes using the existing count and backoff.
    3. After the final failed attempt, urllib3 returns the response.
    4. The private or public request handler calls raise_for_status().
    5. Existing instagrapi status handling raises a typed exception, such as ClientThrottledError for HTTP 429.
    6. For public requests, an adapter-exhausted configured status is re-raised immediately instead of starting another full retry package.

    Error handling

    Connection, TLS, DNS, and timeout exhaustion remain transport errors because they do not have a final HTTP response to map. Only status-based retry exhaustion changes. Unknown HTTP statuses continue through the existing ClientError fallback.

    Private HTTP 429 handling remains body-aware. A response whose message contains Please wait a few minutes maps to the existing PleaseWaitFewMinutes exception; other 429 responses map to ClientThrottledError. Login already handles both.

    The optional curl public transport does not use the urllib3 retry strategy and is unchanged. Feature code that calls self.private or self.public directly will now receive the final retryable-status response instead of RetryError, but remains outside the central typed handlers by design.

    Testing

    Use test-driven development:

    Add focused coverage in tests/regression/test_retry.py:

    1. Assert that both constructed retry strategies set raise_on_status to False while preserving totals, backoff, allowed methods, and status lists. Exercise both the current allowed_methods path and the compatibility method_whitelist fallback by making the first Retry construction raise TypeError in a focused unit test.
    2. Exercise an actual Requests HTTPAdapter against a local deterministic HTTP endpoint that always returns 429. Set backoff to zero, assert that the configured number of attempts occurs, and assert that the final response is returned instead of RetryError escaping.
    3. Pass a 429 response through _send_private_request() and _send_public_request() separately. Assert that both raise ClientThrottledError, retain the final response on the exception, and do not leak RetryError. These handler-level tests complement the adapter-level test without requiring a local TLS server for the private API's fixed HTTPS URL. Add a second private response body containing Please wait a few minutes and assert PleaseWaitFewMinutes.
    4. Exercise public_request() with a persistent 429 and assert that the default configuration performs exactly session_retry_total + 1 attempts. Set session_retry_total=0 separately and assert that the existing outer public_request_retries_count loop still applies.
    5. Repeat the public exhaustion assertion for HTTP 503 and confirm that the final response becomes ClientError without duplicate retry packages.
    6. Exercise _send_public_request(stream=True) against the local 429 endpoint. Assert that retry exhaustion maps to ClientThrottledError; for a successful response, assert that the response remains open and its body is not consumed.
    7. Exercise connection exhaustion against a closed local port and assert that it remains ClientConnectionError rather than a status-mapping exception.
    8. Update live-test expectations that currently special-case RetryError for retryable HTTP statuses. Match the final typed ClientError by response status and endpoint while retaining defensive RetryError coverage where tests intentionally model a generic Requests failure.
    9. Run the focused regression file, the full regression suite, and the project lint checks.

    The tests must be observed failing before the production change and passing after it.

    Compatibility and rollout

    The change uses an urllib3 Retry argument available in the supported urllib3 versions and is independent of Python version. No migration or configuration change is required. Release notes should describe this as exception-mapping correctness, note that configured status retries no longer stack with the outer public retry loop, and avoid presenting it as a workaround for Instagram throttling.

    Engineering review

    What already exists

    • PrivateRequestMixin and PublicRequestMixin already build and mount urllib3 Retry strategies. The change reuses those builders instead of adding a new retry layer.
    • _send_private_request() and _send_public_request() already own HTTP status mapping. The change restores their ability to see the final response.
    • login() already catches both ClientThrottledError and PleaseWaitFewMinutes around pre_login_flow(), so no login policy change is needed.
    • public_request() already owns the application-level public retry loop. It receives one explicit guard against repeating an adapter-exhausted status.
    • Client.set_retry_config() already rebuilds both adapters, so no new public configuration is needed.

    Failure modes

    Failure Planned test Existing handling Caller result
    Persistent private 429 Yes Private HTTP mapping ClientThrottledError or PleaseWaitFewMinutes
    Persistent public 429 Yes Public HTTP mapping ClientThrottledError after one retry package
    Persistent public 503 Yes Generic public mapping ClientError after one retry package
    Closed port or DNS failure Yes Connection mapping ClientConnectionError
    Streaming public 429 Yes Public HTTP mapping before stream return ClientThrottledError
    Legacy urllib3 constructor path Yes method_whitelist fallback Same final-response contract

    No failure mode is silent, unhandled, and untested after the planned coverage.

    NOT in scope

    • Changing the configured retry totals, status list, backoff formula, or Retry-After behavior. Those are existing public settings.
    • Refactoring every feature mixin that calls a raw Requests session directly. Those flows do not pass through the central handlers and need endpoint-specific work if a concrete report shows incorrect mapping.
    • Adding retry behavior to the optional curl transport. It has a separate adapter and is unaffected by this urllib3 defect.
    • Diagnosing or bypassing the account, IP, or risk-state reason for an Instagram rate limit. The library only exposes the server response correctly.
    • Redesigning the full public retry API. This change only prevents the two existing retry layers from repeating the same configured status.

    Parallelization

    Sequential implementation, no parallelization opportunity. The regression tests define the contract, the request mixins make them pass, and live-test/docs updates then align with the new exception behavior.
